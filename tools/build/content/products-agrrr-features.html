The twelve that matter

Twelve features do the work. Each one below opens with a single plain sentence for anybody who just wants a website, and then says the more technical truth underneath. Ten of the twelve are on film: the screenshots come from AGrrr! wearing its dark Hallowe'en theme, mid-session on a real composition. If you would rather follow a build step by step, the first-website guide and the filmed build of the AG website both walk the whole road.

It runs on your desktop, offline

AGrrr! is a program you install on your own Windows PC, and every part of it — placing, editing, building — works with the network cable pulled out.

The app is a small native binary that uses your system's own web view instead of shipping a browser inside the installer. Projects live in ordinary folders on your disk — page source as plain files, metadata in a local database beside them. The core never makes a network call; the network is used exactly twice, both times on your explicit orders: when you point the app at a model you chose, and when you deploy to the host you own. There is no account to create and nothing is synced anywhere.

Drag, drop, and judge the real page

You arrange blocks on a page that is already rendering exactly the way a browser will render it, so the version you are judging is the version visitors get.

The canvas is a live render, not a sketch or a schematic: an unstyled box on it is a genuinely empty box, and a heading wears its real face at its real size. Every placement compiles into production-ready HTML, CSS and JavaScript as you work, so the page you see mid-session is the page the export writes, byte for byte.

A library of ready-made blocks, no AI required

More than 1,200 finished, pre-validated blocks — heroes, forms, timelines, menus, effects — wait in a searchable library, and not one of them needs artificial intelligence to work.

Every record in the library is pre-written and passes the same validation gate before it can reach your page. You search it offline, read the record's facts and live preview, drop it onto the canvas, and put your own words into its parameters; anything you write yourself can be saved back into your own library as a first-class block.

One theme dresses every page, dark and light

You pick the colours, fonts and spacing once, and every page on the site wears them — and switching the whole site between dark and light is one swap.

A theme is an 18-token vocabulary: colour roles, title and body faces, spacing and corner values. Pages inherit the vocabulary rather than copied styles, so re-dressing the site is one panel edit instead of a dozen pages of retouching. Dark and light sets ride the same tokens, and any value the panel does not name can be authored as a custom property. The screenshots on this page are the proof: the whole application re-dressed for the season in one theme.

The canvas measures itself in real screen units

The canvas reads the same units a browser reads, so a panel placed at two thirds of the view really is two thirds of the view on the built site.

Placements are authored and reported in vh and vw, the viewport units the compiled CSS carries. The tracked canvas adds measuring tapes and a red-edged overlay at a picked viewport size — Desktop wide 1920 × 1080 among them — and a selected block's read-back badge reports its seat against that viewport. It is the instrument the composition is refined against before anything ships.

Small screens are decided, not improvised

When the site meets a phone or a tablet, AGrrr! proposes how each element should behave, you answer each proposal, and the app refuses to ship while a decision is still open.

The scaling engine reads the composition and proposes small-screen behaviour element by element; nothing exports while a proposal is unanswered. The Responsive tab holds the device views and the decision queue together — pick a width, read the proposal, settle it — and the result is checked live at every width the strip carries.

Elements that answer: links, actions and defended forms

Buttons press, links lead and forms submit — and the parts that talk to a server arrive with the defences a public page needs built in.

Interactive elements are linked actions, and their behaviour is authored where the element is described: select a form and the Properties panel's Behaviour section carries where it submits and how, select a button and its type is a choice, not a script. Forms compile to PHP handlers that run on ordinary shared hosting, backed by a database on your host, with a honeypot field and rate limiting standing in front of the mailbox. A drag-and-drop consent banner ships with a compile-time gate, so non-essential scripts genuinely wait for the visitor's yes.

Multi-page sites with the navigation derived for you

Build several pages and the site's menu builds itself — add a page and it appears in the navigation, and the page you are on shows as current.

The compiler derives the navigation tree from the project's pages, so the menu can never drift from the pages that exist. The same tree rides the export as a menu-tree.json payload for the site's search and any script that wants it. Each page's actions menu carries its name, its route, its head metadata and which page is home.

Exports plain HTML, CSS and JavaScript — the same bytes every time

What you end up with is ordinary website files that any host on earth accepts, and rebuilding the same composition hands you the very same files again.

The compile is deterministic: same composition, same bytes, file for file, which makes rebuilds boring and diffs meaningful. Export runs for a single file or the whole site, with the delivery files a real site wants — .htaccess, robots.txt, a 404 page and a handover README that says exactly what the app cannot know about your host. The gate above the panel is the promise: a page that has not settled its questions does not leave the app.

Runs on ordinary shared hosting, PHP where it counts

The finished site runs on the cheap hosting plan you probably already have — and where a static page is not enough, AGrrr! writes the server side for you.

The compiled output is static HTML, CSS and JavaScript, which every shared host serves without complaint. Contact forms and anything that must remember something compile to PHP handlers for that same shared host, with SQLite standing in locally while you work. Deployment goes straight from the panel over FTP or SFTP to the host you own — the form below is where your host's connection details go, once.

AI is optional, and the key is yours

The whole app works with no artificial intelligence at all, and if you ever want a model's help, you plug in your own key from your own provider.

There is no bundled model and no mandate to use one: the canvas, the library, the compiler and the export all work with zero providers configured, and that is the floor rather than a degraded mode. When you do connect one, it is bring-your-own-key — Anthropic, OpenAI, Gemini, OpenRouter, or a local model through the OpenAI-compatible adapter — kept in the app's own backend and never inside the page it reviews. Its suggestions arrive as diffs you accept or reject one by one; it never generates your site from scratch and never touches your work without your confirmation. No single company's model, bill or terms of service sit between you and your own site.

Version history that keeps the messy first pass

Every named version of your pages is kept for good, so the brave experiment and the rough first draft stay reachable however much you change later.

History is append-only: a named version is permanent, the newest versions survive any amount of thrashing, and the first snapshot of every session is never discarded. Comparing and returning are one-panel operations, so the undo of last resort — back to this morning's shape — always exists.
